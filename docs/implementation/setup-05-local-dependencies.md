# SETUP-05 — local dependencies and restricted bootstrap

12 October 2026. Implements [SETUP-05](001-development-environment-and-project-foundation.md#setup-05--local-dependencies-database-bootstrap-and-isolated-transports), following the unchanged core baseline and SETUP-04 composition boundaries.

`infra/compose` runs only PostgreSQL, one SeaweedFS server and Mailpit by default. Tags and immutable index digests match the qualified inventory. Named volumes retain PostgreSQL 18's cluster directory, SeaweedFS data and filer metadata (the pinned image's `/data` working directory), and Mailpit's SQLite capture database. All host ports bind IPv4 loopback. API, worker and Metro remain host processes. The optional `diagnostics` profile adds a pinned local OTel collector with no external exporter or log pipeline.

Provisioning is an explicit local development operation using credentials from the ignored infrastructure file. It creates purpose-specific login roles and non-login object/helper owners, confines owner membership to the migrator, revokes public database/schema access, and revokes default function execution. Runtime configurations have only their own role URLs. `packages/db/src/release.ts` is a separate tooling entry, absent from the DB package export surface and runtime roots.

The checked `0001-foundation.sql` baseline and its SHA-256 registry establish a private migration marker, schema usage and exact queue grants. SQL uses LF bytes; no historical documents were renormalized. Bootstrap serializes provisioning and migration entry with advisory locks. pg-boss performs its own transactional schema installation only in the release step; the marker/grants commit together afterwards. If release fails before the marker, rerun the same reviewed release. A completed marker must match exactly; repeated release verifies history and queue compatibility and does not silently repair grant drift. Later changes require new reviewed versioned migrations and an updated registry/runner.

pg-boss 12.37.1 uses schema version 45 and shared `job_common` storage. Release creates exactly one synthetic queue. API producer grants permit SELECT/INSERT on job storage and metadata reads. Queue execution can maintain jobs, dependencies, instances and warnings; only supervision counters/timestamps can change on queue/version metadata. Queue creation, queue policy changes, schema-version changes, truncation and DDL remain denied. Runtime uses `migrate:false`, `createSchema:false`, `reindex:false`, no schedules and no persisted queue-stat partitions. Producer supervision and instance registration are disabled; consumers retain supervision and registration. The handler validates an opaque synthetic fixture ID and has no side effects, making repetition harmless.

The DB package provides bounded `pg` pools and a Drizzle factory. There are no product schemas/models, generic repositories, household transaction wrappers, auth tables or product RLS here. The integration suite creates a random database on a separate disposable Compose project, provisions actual credentials, and creates its protected RLS table only inside that test database. It checks missing context and connection reuse after commit/rollback; this cannot establish the full product authorization contract.

API readiness and worker heartbeat inspect current role identity, privileged membership, ownership, schema usage, the complete baseline marker, pg-boss version/queue and required/forbidden grants. Storage and Mailpit reachability are bounded HTTP checks; local SMTP delivery is separately qualified. Queue errors fail readiness until restart. Preparation, HTTP readiness and worker shutdown have existing process bounds; pools have finite connection/statement/query limits. At one API plus one worker, configured pools permit at most twelve DB connections (six per process), without a dedicated listener. Release/test connections are separate headroom.

SMS/OTP, AI and speech test adapters accept only the named synthetic fixture. The email adapter sends a fixed content-free message to local Mailpit. Both pure process parsers and adapter creation reject test transports in pilot/production. No live-provider SDK, credential, send, prompt or household fixture is present. Shared Pino redaction retains stable codes/correlation and removes content, OTPs and credentials. The local collector accepts a synthetic OTLP trace after attribute/event/link removal; application SDK instrumentation and production monitoring remain later work.

See [the runbook](../development/setup-05-runbook.md), [validation](../development/setup-05-validation.md) and [evidence](../development/evidence/setup-05-2026-10-12/README.md). These are development infrastructure checks, not product or pilot admission.
